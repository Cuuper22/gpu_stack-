# Causal Observatory recovery v2 contract

Status: design contract, July 12, 2026. Pure recovery contracts and a transition
runtime substrate exist; no E001 recovery runner, v2 result artifact, projector,
or browser reader exists yet.

## Purpose

This contract defines how GPUSTACK may expose recovery-aware virtual
datacenter mechanics without implying that recovery preserves learning quality.
It covers:

- mid-operation failure and preemption;
- completed but unrecoverable work;
- checkpoint selection and restore;
- replay of lost work;
- site membership removal and rejoin;
- training-state transfer;
- recovery debt against a matched no-failure counterfactual.

The observatory remains an evidence projection. The browser formats and
navigates artifact values; it does not infer preemption, reconstruct lost work,
sum recovery debt, or decide whether a gate passed.

## Current v1 boundary

The present engine reserves an assumed outage interval before scheduling
flexible work. A conflicting operation moves after the outage as one indivisible
event. The current `recovery` event is an availability marker, not checkpoint
restore, replay, membership repair, or recovery completion.

Therefore a v1 artifact must continue to say that these mechanisms are
unmodeled. A UI must not reinterpret positive `wait_ns`, checkpoint traffic, a
zero-duration recovery event, or generic state-transfer bytes as recovery
semantics.

## Truth vocabulary

Three different moments must remain distinct:

1. **Availability recovery:** the assumed scenario time when failed resources
   become available again.
2. **Durable-progress recovery:** the modeled post-failure time when the run
   first reaches the episode's serialized shared durable-frontier target after
   all required restore, transfer, replay, and resynchronization work.
3. **Site rejoin:** the modeled time when the recovered site is admitted back
   into membership with a compatible state version. A policy may recover
   durable progress without ever rejoining the site.

None of these means loss recovery, capability recovery, convergence recovery,
or held-out learning validation.

## Evidence classes

The existing observatory evidence grammar remains authoritative.

| Signal | Evidence class | Required visible wording |
|---|---|---|
| Outage start, end, site, and cause | `assumed` | `ASSUMED` |
| Absolute checkpoint trigger schedule, configured checkpoint size, failure policy | `assumed` | `ASSUMED` |
| Preemption, lost-work accounting, restore, replay, membership action, transfer, resynchronization, recovery debt | `modeled` | `MODELED` and `conditioned on ASSUMED outage` |
| Attached real trace in a future artifact | `observed` | `OBSERVED` plus provenance |
| Learning impact of the recovery episode | `unmeasured` | `UNMEASURED` |
| Delay-response sensitivity used elsewhere in E001 | `prior` | `PRIOR · NOT FITTED` |

Do not introduce a `mixed` evidence class. A recovery episode is a composite:
its outage input is assumed, its mechanics are modeled, and its learning effect
is unmeasured. Each field carries its own class or an explicit conditioning
reference.

## Schema version and optionality

The recovery contract is a breaking semantic expansion and uses:

```text
gpu-stack.causal-observatory.e001.v2
```

Recovery fields are optional because a run may be generated by an engine that
does not implement them. Optional does not mean ambiguous:

- missing recovery block plus `status: unsupported` means the producer does
  not model the capability;
- an empty array plus `status: supported` means the capability exists but this
  run contains no matching episode or event;
- `null` is used only when a field is explicitly not applicable and must be
  accompanied by a reason;
- unavailable measurements use evidence status, never numeric zero;
- the browser never manufactures a recovery block for a v1 artifact.

In v2, `policy_registry` and `mechanics_capabilities` are required. The policy
registry has exactly the six identifiers and roles below. The oracle role may
never be rendered as a fixed baseline or included in fixed-baseline superiority.
The remaining recovery blocks are conditionally required by capability state.

Allowed capability states are `supported` and `unsupported`. A supported
capability requires internally consistent event references and the fields
defined below. Unsupported capabilities require a non-blank boundary.

both controller-visible and engine-private snapshot streams; supported
membership response requires policy decisions referencing controller-visible
snapshots; supported checkpoint lineage requires complete manifests; supported
byte accounting requires all six traffic classes plus raw numerator and
denominator. An empty supported array is valid only when the run contains no
applicable outage, decision, checkpoint, or transfer.

`policy_role` is exactly one of `baseline`, `candidate`, or
`oracle_comparator`. `adaptive-recovery` is the only candidate. The four
non-clairvoyant comparators are baselines. `future-trace-recovery-oracle` is the
only oracle comparator and participates in completeness, never fixed-baseline
superiority.


`record_type` is one of:

- `event`: resource-consuming or scheduled temporal work;
- `intervention`: a controller decision such as membership removal;
- `milestone`: a zero-duration fact such as preemption or durable-progress
  recovery.

`recovery_role` is one of:

- `primary_compute`;
- `failure`;
- `preemption`;
- `checkpoint_write`;
- `checkpoint_restore`;
- `state_transfer`;
- `replay`;
- `membership_remove`;
- `membership_rejoin`;
- `resynchronize`;
- `availability_recovery`;
- `durable_progress_recovery`.

The producer may add other roles only through a schema revision. UI code does
not infer roles from event-name substrings or arbitrary metadata.

### Work accounting invariant

At terminal completion with no work in flight:

```text
attempted_compute_flops
  = valid_final_state_compute_flops + lost_compute_flops
```

`replay_compute_flops` is a labeled subset of attempted compute. Each attempt
records `planned_compute_flops`, `executed_compute_flops`, valid and lost
portions, original-versus-replay kind, causal outage IDs, and exactly one
terminal disposition: `completed`, `preempted`, `aborted`, or
`invalidated_after_commit`. Never classify unstarted work as lost. Recovery may
invalidate committed work on healthy sites if it is newer than the selected
manifest, so `attempt_dispositions` includes every affected work unit, not only
work at the initially failed site.

Repeated failure appends another ordered outage to the same joint episode and
new restore or replay attempts with distinct IDs. It never mutates an earlier
terminal disposition or reuses an attempt ID.

### Checkpoint restore status

`checkpoint_restore.status` is one of:

- `executed`: a complete manifest hash/reference, at least one restore attempt,
  exact local and remote byte totals, restored state IDs, verification time, and
  resolvable event references are required;
- `not_required`: a non-blank reason is required and restore values are absent;
- `unsupported`: the capability boundary is repeated and no restore result is
  implied.

A checkpoint write event does not prove that a usable checkpoint exists.
Checkpoint identity, manifest hash, state version, durable logical step, exact
shards, trigger and commit times, and restored state must be explicit. Repeated
failure during restore appends a new immutable restore attempt; it does not
overwrite the interrupted attempt's bytes or disposition.

### Recovery debt definition

Recovery debt is a matched mechanics counterfactual, not outage duration and
not time to a learning target. The paired run must use the same policy, engine
source, seeds, workload, and scenario inputs except for the named removed
outage events. Both runs target the exact serialized `durable_frontier_target`;
the actual anchor must occur after the episode's first physical failure.

`recovery_debt_ns` is signed and must never be clamped in the artifact or UI. A
negative value is displayed as a negative mechanical delta and flagged for
interpretation; it is not silently renamed zero debt.

Component intervals may overlap because restore, transfer, replay, and healthy
site work can execute concurrently. Their sum is not recovery debt. Only the
matched anchor delta is authoritative. Overlapping or repeated failures before
durable recovery form one joint episode and are removed together. If either run
never reaches the shared target, the metric is unresolved rather than zero or
infinite.

## Run-level metrics

When the corresponding capabilities are supported, each run reports these
engine-computed metrics in `runs[].metrics`:

| Metric | Unit | Meaning |
|---|---|---|
| `attempted_compute_flops` | FLOP | All physically executed compute |
| `valid_final_state_compute_flops` | FLOP | Executed compute retained in terminal durable state |
| `lost_compute_flops` | FLOP | Executed compute invalidated by failure or rollback |
| `replay_compute_flops` | FLOP | Replay-labeled subset of attempted compute |
| `completed_collective_link_bytes` | byte | Unique link segments from committed collectives |
| `aborted_collective_link_bytes` | byte | Unique link segments from uncommitted collectives |
| `remote_checkpoint_replication_link_bytes` | byte | Cross-site checkpoint-write segments |
| `remote_checkpoint_restore_link_bytes` | byte | Cross-site checkpoint-read segments |
| `recovery_state_redistribution_link_bytes` | byte | Cross-site recovery hydration or resharding |
| `planned_state_migration_link_bytes` | byte | Non-recovery planned migration segments |
| `total_inter_site_link_bytes` | byte | Exact sum of the six disjoint link-byte classes |
| `synchronous_recovery_baseline_total_inter_site_link_bytes` | byte | Matched synchronous raw denominator |
| `total_inter_site_byte_fraction` | 1 | Candidate raw total divided by matched synchronous raw total |
| `checkpoint_restore_bytes` | byte | Local plus remote bytes read from a committed manifest |
| `membership_removed_site_ns` | site·ns | Desired-member time excluded from physical execution membership |
| `recovery_debt_ns` | ns | Signed matched shared-frontier anchor delta |
| `recovery_episode_count` | 1 | Number of recovery episodes |

The link-byte identity is exact:

```text
total_inter_site_link_bytes
  = completed_collective_link_bytes
  + aborted_collective_link_bytes
  + remote_checkpoint_replication_link_bytes
  + remote_checkpoint_restore_link_bytes
  + recovery_state_redistribution_link_bytes
  + planned_state_migration_link_bytes
```

Every physical link-direction segment has one segment ID and one traffic class.
Retries retain their traffic class and receive new segment IDs. Local restore
I/O is present only in `checkpoint_restore_bytes`.

## Structured evidence requirements

The recovery-v2 protocol expands
`e001-collective-and-failure-model-admission` to require:

- both raw total-byte values, the ratio, and all six disjoint traffic classes;
- panels for algorithm-specific completed collectives, collective interruption
  during latency and payload, mid-operation compute failure, rollback after
  committed work, checkpoint restore, replay accounting, membership response,
  state movement, and recovery debt;
- evidence references into the recovery episode, timeline, policy decisions,
  and counterfactual result.

It may resolve at the virtual stage once every required modeled boundary is
present.

The five dedicated recovery gates retain the exact frozen panel names in
`E001_RECOVERY_V2_PROTOCOL`. An episode links to every applicable gate; it does
not cite only the two pre-v2 requirements.

`e001-full-boundary-nonreversal` remains unresolved at the virtual stage even
after recovery mechanics exist. It requires controlled recovery evidence and
metered facility energy. `e001-heldout-learning-transfer` also remains
unresolved.

`policy_decision_regret` is also unresolved. The observatory must not display a
regret number until a separate protocol freezes the scalar objective, units,
horizon, normalization, tie handling, and oracle action space.

The UI reads `experiment_artifact.conclusion` and structured requirement
results. It never declares survival because scalar falsifiers passed or because
a recovery episode exists.

## Existing-view absorption

| Signal | Existing observatory view | Required treatment |
|---|---|---|
| Failure preemption | Causal field, policy timeline, evidence inspector | Split the attempt at failure and show an explicit preemption milestone |
| Lost work | Timeline hatch, recovery inspector, comparison recovery cell | Show work completed but unrecoverable; do not hatch deferred work |
| Checkpoint restore | Timeline, site rail, evidence inspector | Show checkpoint identity, age, state version, source, target, bytes, and duration |
| Replay | Timeline, causal field, recovery inspector | Link every replay attempt to the original attempt |
| Membership remove/rejoin | Site rail, timeline milestones, policy decision ledger | Site state follows selected time; ledger shows visible input and before/after membership |
| State transfer | Site rail, WAN link, timeline, evidence inspector | Show state ID/version and source/target; distinguish recovery transfer from collective traffic |
| Recovery debt | Policy comparison, timeline bracket, causal field, inspector | Show matched counterfactual delta and non-additive component intervals |
| Evidence admission | Comparison conclusion and structured requirement section | Show failed and unresolved mandatory gates even when scalar gates pass |
| Learning effect | Existing residual panel | Keep empty and explicitly unmeasured |

### Causal field

The v2 causal reading order is:

1. assumed site availability changes;
2. in-flight attempts preempt and some completed work becomes unrecoverable;
3. membership and state placement change;
4. a durable checkpoint is selected and restored or transferred;
5. lost work replays and the run resynchronizes;
6. durable mechanical progress recovers with an explicit counterfactual debt;
7. learning impact remains unmeasured and confirmatory gates remain unresolved.

Artifact nodes should add `failure_preemption`, `durable_state`,
`state_placement`, `replay`, and `recovery_debt`. The existing `membership` node
changes from `unmeasured` to `modeled` only when membership interventions are
actually present and admitted by the capability contract.

### Site rail

At the selected timestamp, each site shows:

- observed health and engine-private physical health as separate labeled rows;
- desired membership, observed effective membership, and physical execution
  membership as separate states;
- owned state versions;
- active restore or transfer;
- rejoin readiness.

Availability, observation, readiness, and membership are separate. A recovered
site may remain excluded, and an excluded site must not look failed merely
because it is inactive. Engine-private physical state is post-run evidence and
never appears in a snapshot referenced by a candidate decision.

### Timeline

The same aligned policy timeline absorbs all recovery roles. Preemption,
membership decisions, and recovery completion are milestone markers. Restore,
state transfer, replay, and resynchronization are duration intervals. A bracket
connects failure to durable-progress recovery; a second optional marker shows
site rejoin.

The no-failure counterfactual may appear as a restrained reference marker or
ghost interval, but its exact values and hash come from the artifact.

### Policy decision ledger

The ledger stops deriving decisions from cadence changes. It renders
`policy_decisions` in sequence order and includes:

- decision time;
- modeled state visible to the controller;
- action;
- membership before and after;
- state-version precondition;
- effective interval;
- evidence class and reason.

No row may say `after failure detected` unless a referenced visible-state
snapshot proves the controller observed the active failure.

## Recovery comparison compound cell

The policy comparison adds one column, `Recovery mechanics`. It does not add a
column for every recovery metric.

Collapsed cell anatomy:

```text
+16.0 s recovery debt
MODELED · conditioned on ASSUMED outage
4.0 PFLOP lost · 4.0 PFLOP replayed · 2.24 TB restored
failure-model admission: UNRESOLVED
```

Rules:

- the first value is artifact `recovery_debt_ns` formatted as time;
- a negative value remains negative and is called a mechanical delta;
- secondary values are omitted, not replaced with zero, when unavailable;
- `no recovery episode in this trace` is distinct from zero debt;
- unsupported capability displays `UNMEASURED · recovery model unavailable`;
- absent artifact displays `not run`;
- activating the cell selects its recovery episode and opens the inspector;
- the mandatory structured gate and artifact conclusion remain visible.

On mobile this remains one horizontally scrollable comparison column. Detailed
components belong in the sheet, not additional table columns.

Depth changes explanatory density only. Values, evidence classes, requirement
states, and conclusions are identical at every depth.

## Learning-residual non-claim boundary

The existing learning residual panel remains an honest empty plot until a
held-out multi-site learning observation is attached. Recovery mechanics do not
create a point, curve, residual, interval, or confidence band.

Required copy:

```text
No held-out multi-site learning observation.
Mechanical recovery was modeled; learning recovery is unmeasured.
No residual can be computed.
```

Do not project recovery debt into time to loss target. Do not interpret replayed
FLOPs as recovered learning progress. Do not let successful mechanical recovery
resolve `e001-progress`, `e001-time`, or the held-out transfer requirement.

## Mobile and accessibility rules

- Recovery milestones may be zero-duration but must have at least a 44 by 44
  pixel transparent hit target.
- Marker shape and text carry role; color is never the only signal.
- Group the accessible timeline fallback by policy and recovery episode. A flat
  list of every compute segment is not usable.
- Arrow-key order follows time within the selected policy. Enter opens the
  selected event or milestone.
- Do not auto-open the mobile evidence sheet while scrubbing. Open only after
  explicit event, episode, site, or comparison-cell activation.
- Escape closes a transient sheet and returns focus to its invoking marker.
- Throttle live-region updates during pointer scrubbing. Announce the committed
  timestamp and state, not every intermediate pixel.
- Site labels must separately announce health, membership, and state readiness.
- Component durations must include the text `may overlap; do not sum` in the
  inspector and accessible table.
- The causal path remains vertical on mobile. Only the site rail, comparison,
  and timeline may pan horizontally.
- Dense raw IDs appear only at Full trace depth, but every essential conclusion
  and evidence class remains available without hover.
- Reduced-motion mode disables interpolated scrubber, site-state, and sheet
  transitions.
- A deep link may use the existing `node=recovery:<episode_id>`, `policy`,
  `event`, and `time` URL state. A new query parameter is not required.

## Schema migration strategy

Implementation status on July 12, 2026: the focused four-policy slice now has a
separate content-addressed v2 result and projection; the v1 artifact remains
unchanged; and the dual reader renders recovery only from the v2 artifact.
Unresolved protocol requirements remain explicit in the artifact rather than
being claimed as completed migration phases. The next product input is observed
learning evidence, not another schema expansion.

### Phase 1: engine and artifact model

1. Integrate the transition runtime substrate into a new E001 recovery-v2 runner
   without changing the v1 runner.
2. Connect durable checkpoint/state-version records, restore and replay
   planning, persistent failure decision epochs, membership interventions, and
   state catch-up rules to that runner.
3. Produce matched same-policy no-failure counterfactuals.
4. Validate work-accounting identities, event references, policy-visible state,
   state-version compatibility, and recovery-debt pairing.
5. Keep the existing v1 projection unchanged.

### Phase 2: dual artifact generation

1. Generate a separate v2 observatory artifact while retaining the v1 artifact.
2. Require `mechanics_capabilities` in v2.
3. Include optional recovery blocks only when their capability contracts are
   satisfied.
4. Include every new field in the artifact SHA-256.
5. Preserve source-result, scenario, engine-source, and counterfactual hashes.

### Phase 3: dual reader

1. Teach the observatory parser to accept v1 and v2 explicitly.
2. Route v1 to the existing whole-operation-postponement copy.
3. Route v2 through capability states; never infer missing v2 blocks.
4. Keep existing URL state stable.
5. Render recovery UI only from a valid v2 artifact.

### Phase 4: switch and retire

1. Switch the published data path only after a real v2 artifact exists and the
   complete recovery UI is ready for feature-level verification.
2. Retain v1 fixtures for compatibility tests and truth-regression checks.
3. Retire v1 publication only after downstream consumers declare v2 support.

## Artifact acceptance invariants

A v2 recovery artifact is invalid unless all applicable invariants hold:

- every timeline recovery reference resolves to exactly one joint episode;
- every episode references all ordered causal outages and its matched
  counterfactual;
- attempted compute equals valid-final-state plus lost compute within declared
  numerical tolerance, with replay a labeled subset;
- the six disjoint traffic classes sum exactly to total inter-site link bytes,
  and both raw numerator and denominator reproduce the serialized fraction;
- every replay attempt references an original attempt and does not reuse its ID;
- every attempt has exactly one immutable terminal disposition, including
  invalidation after commit;
- every executed restore references a complete content-addressed manifest,
  exact shards, and state-lineage hashes;
- every membership decision references a controller-visible snapshot that
  contains no engine-private physical fields;
- rejoin does not become effective before required state compatibility;
- recovery-debt anchors refer to the same serialized durable-frontier target,
  and the actual anchor occurs after the episode's first physical failure;
- overlapping or repeated pre-recovery failures are paired as one joint causal
  bundle unless a separate marginal estimand is preregistered;
- overlapping component intervals are not summed into debt;
- run-level recovery metrics reconcile with episode summaries;
- mandatory structured evidence results and `experiment_artifact.conclusion`
  are preserved unchanged in the observatory projection;
- `status.held_out_learning_validation` remains false until held-out learning
  evidence actually exists;
- the learning residual remains empty while that status is false.

Until these invariants can be produced and validated, the correct observatory
state is the existing v1 statement: whole operations are postponed and recovery
mechanics are unmodeled.
